# narration-style.md — 口調・テンポ・用語統一

Kyozai-Athanor配下の教材ナレーションに共通して適用する文体ガイド。

## 基本トーン

- 講師の声を想定したナレーション
- 「である」調ではなく「ですます」調基準（教育的場面のため）
- ただしYouTube一般向け派生では「ですます」混じりのカジュアル可
- 専門用語の初出時は必ず日常言葉で言い換えてから定義する

## テンポ

- 1スライド30〜60秒目安
- 短尺形式（総尺2分未満のショート教材）は「1スライド30〜60秒」の適用除外とする（パイロット java-vs-js 実績: 約15〜22秒/枚、2026-07-10）
- 5秒以上の沈黙NG、ただしフローチャート読解等の思考時間は5秒の間を意図的に置く
- 「ここ、大事ですよ」のような注意喚起は1章に1回まで（多用すると効果が薄れる）
- 発話速度目安：**460〜500 文字/分（VOICEVOX 実測による標準値）**
  - 旧値は 350 文字/分だった。これは固定台本向けの推定値（`docs/specs/kosen-w12-system-dev/requirements.md`
    NF-04 参照）だったが、audio-first 化によりスクリプトエンジンでの実測が基準となった
    （2026-07-13、W5-script-engine-T23）
  - `docs/specs/script-engine/design.md` §9.1 の執筆時ラフ予測式が採用する
    `speech_rate_base = 480 文字/分` は、この実測レンジ 460〜500 文字/分の中央値近傍を採用した値であり、
    本目安と整合する

## 用語統一表

| 推奨表記 | 非推奨表記 | 備考 |
|---|---|---|
| プログラム | コーディング・コード | 学生視点では「コーディング」だが、「プログラム」のほうが広い |
| 要件定義 | 要件の決定・要求分析 | 業界標準語 |
| ヒアリング | 聞き取り（混用可） | 章タイトルでは「ユーザー聞き取り」で良い |
| プロトタイプ | 試作・モック | 初出時に「試作品」と添える |
| 個人情報 | プライバシー情報 | 法用語と日常語を区別 |
| 個人情報取扱事業者 | 個人情報を扱う会社 | 法用語は正確に |
| 電気通信事業者 | 通信会社 | 法用語と日常語を区別 |

## NG表現

- 「絶対」「必ず」を法令解釈で使わない（例外があるため）
- 「簡単」「すぐできる」を初学者向けに使わない（できなかった時に劣等感を持たせる）
- 「みなさん、わかりますよね？」のような同意強要

## 受講者層別の語彙調整

### 高専・電気情報系
- 「コーディングが全てではない」のメッセージを必ず入れる
- C言語・組込み・回路図への言及を歓迎
- 「現場ではこうやる」エピソードに反応する

### 高専・非情報系（建築・機械等）
- 専門用語はその場で定義
- 「あなたの分野でも同じ構造がある」と接続する
- フローチャートは「設計図」と並べて説明

### YouTube一般
- 高専固有の話題を抜く
- 例え話を厚くする
- 5〜10分の章単位切り出しを意識した話の区切り

## 引用と典拠の言い方

- 法令引用：「個人情報保護法では、〜と定められています」
- 政府ガイドライン：「経済産業省のAI事業者ガイドラインによると、〜」
- 不確実な箇所：「2026年6月時点での話ですが」「定説では〜とされています」

## オープニングとクロージング

### オープニング（5秒以内）
- 章タイトル提示→「今日は〜について話します」程度
- 過剰な自己紹介はYouTube版でのみ

### クロージング
- 章のまとめは3点以内
- 次章への接続を最後に1文
- 「実装は氷山の一角」のメッセージはまとめ章で再強調

## 尺予測の許容誤差運用（script-engine, design §9.2-9.3 委譲分）

> 本節は script-engine Milestone（D-20）の design.md §9.2-9.3 で確定した運用ガイドを、
> `docs/conventions/` 側の恒久的な参照先として転記したものである
> （`docs/specs/script-engine/tasks.md` W1-script-engine-T20 完了条件）。
> 発話速度の基準値そのもの（本ファイル冒頭「テンポ」節）の改訂は別タスク
> （W5-script-engine-T23）の対象であり、本節では扱わない。

script-engine の台本コンパイラは、執筆時のラフ予測（文字数ベース）と VOICEVOX WAV 実測後の
総尺を比較し、誤差率に応じて 3 段階で扱いを分ける。

| 誤差率 | 扱い | 挙動 |
|---|---|---|
| 15% 以下 | 正常 | メッセージなし |
| 15% 超 〜 25% 以下 | 警告（非ブロッキング） | compile コマンドの標準出力に表示、続行可能 |
| 25% 超 | 強い警告 + エスカレーション（非ブロッキング） | 目立つフォーマットで表示。exit code は変えない（design FR-5 は「警告する MUST」であり「停止する MUST」ではない） |

**±25% 超が継続する場合の運用ガイド（台本分割等の対応目安）**:

- まず `docs/conventions/speaker-profiles.yaml` の該当話者 `speech_rate_factor` が実測に対して
  ずれていないか確認する（パイロット実測後の初期調整値であり、確定値ではない。design §9.2
  「外挿の限界」注記参照）
- `speech_rate_factor` の調整で誤差が解消しない場合、台本エスカレーション手順
  （requirements.md 受入条件 5 改訂版）に従い、台本修正 → 再 compile のリトライを 1 回行う
- リトライ後もなお ±25% 超が続く場合の対応目安（台本分割等）:
  - **台本分割**: 1 台本（1 script-id）内の発話数・想定尺が大きい場合、話者交代頻度や
    掛け合いのオーバーヘッドが誤差に効きやすい。セグメント単位（章単位）で台本ファイルを
    分割し、コンパイル単位を小さくすることで累積誤差の影響を局所化できる
  - **原因分析の記録**: 超過の原因分析を retro に記録し、基準値の見直し（15%/25% の境界値
    自体の変更）が必要と判断される場合は `future-candidates` に登録する（本 Milestone 内での
    基準値変更は行わない、design §9.2）
  - **条件付きクローズ**: 上記対応でも解消しない場合は、ユーザー裁定による条件付きクローズを可とする
    （design §9.3 / tasks.md W5-script-engine-T22 のエスカレーション手順に準拠）
- 標準尺（10〜15 分/本）の台本が複数蓄積された後、`speech_rate_factor` の実測更正・基準値の
  再評価を改めて行う（パイロット規模のみでの確定値扱いはしない、design §9.2）

参照: `docs/specs/script-engine/design.md` §9.1（執筆時ラフ予測の式）/ §9.2（許容誤差基準値の決定）/
§9.3（警告の運用強度）、`docs/specs/script-engine/tasks.md` W1-script-engine-T20 / W5-script-engine-T22。
